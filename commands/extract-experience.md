# /extract-experience 命令

## 命令描述

从当前项目提取经验到 SKILL 文档，用于持续积累和优化产品设计知识库。

## 触发条件

用户输入 `/extract-experience` 或明确要求"提取经验"、"总结经验"、"更新 SKILL"。

## 执行流程

### 1. 识别项目上下文

首先分析当前项目的关键信息：
- 项目类型（Web 应用、移动端、3D 可视化等）
- 技术栈（React、Vue、Three.js、OGL 等）
- 核心功能特性
- 遇到的主要挑战

### 2. 提取踩坑记录

扫描项目代码和对话历史，识别以下类型的问题：

#### 2.1 布局问题
- 移动端适配问题（dvh、安全区域、触摸区域）
- 响应式布局问题（断点、媒体查询）
- z-index 层级问题
- 滚动和定位问题

#### 2.2 交互问题
- 触摸反馈缺失
- 手势冲突
- 动画性能问题
- 状态管理问题

#### 2.3 性能问题
- 首屏加载慢
- 包体积过大
- 运行时卡顿
- 内存泄漏

#### 2.4 3D/WebGL 问题
- Shader 兼容性
- 粒子系统性能
- Canvas 生命周期
- 响应式 3D 场景

#### 2.5 部署问题
- 构建配置
- 单文件打包
- CDN 部署
- 多平台适配

### 3. 格式化踩坑记录

使用 [templates/pitfall.md](../templates/pitfall.md) 模板格式化每个踩坑点：

```markdown
## 问题 N：[问题名称]

### 症状
[描述用户看到的现象]

### 根本原因
[解释为什么会发生这个问题]

### 解决方案
[提供具体的代码示例和修复步骤]

### 验证清单
- [ ] [验证项 1]
- [ ] [验证项 2]
```

### 4. 更新 pitfalls 文件

根据问题类型，将踩坑记录追加到对应的文件。**类型映射表以 [MAINTENANCE.md](../MAINTENANCE.md) 的"类型映射表"为单一信源**，不要在此处维护副本，避免漂移。

如果问题类型不在现有映射表中，创建新的 pitfalls 文件并同步更新 MAINTENANCE.md 的映射表。

### 5. 创建项目案例

使用 [templates/project-example.md](../templates/project-example.md) 模板创建项目案例：

```markdown
# [项目名称]

## 项目背景
[描述项目目标和背景]

## 设计过程
[描述使用的设计流程和工具]

## 关键决策
[列出重要的技术决策和原因]

## 核心成果
[量化项目成果]

## 踩过的坑
[链接到详细的踩坑记录]
```

保存到 `examples/[project-name].md`。

### 6. 更新三处索引（同步闭环）

**重要**：新增踩坑或案例时，必须同步更新以下三个文件，避免"主文档先走、配套滞后"。这是 v2.5.0 起的强制要求。

#### 6.1 SKILL.md
1. **踩坑记录索引** - 添加新的 pitfalls 文件链接
2. **实际案例** - 添加新的项目案例链接
3. **版本信息** - 更新 YAML frontmatter 的 `version` 和 `tags`

#### 6.2 MAINTENANCE.md
1. **文件组织结构** - 文件树补全新文件
2. **类型映射表** - 新增踩坑类型行（仅新增 pitfalls 文件时）
3. **版本示例** - 同步 frontmatter 示例的 version 与 tags

#### 6.3 README.md
1. **核心特性** - 统计数字（"N 个案例 + M 份踩坑"）
2. **文档结构** - 文件树补全
3. **案例概览** - 新增案例条目
4. **踩坑记录索引** - 新增踩坑条目
5. **版本历史** - 顶部追加新版本条目

#### 6.4 同步检查清单

更新完成后逐项核对，任一未通过则回头补：

- [ ] 三处文件树的文件数量一致
- [ ] 三处统计数字一致（案例数 / 踩坑数）
- [ ] SKILL.md 索引条目数 = 实际文件数
- [ ] README.md 踩坑索引条目数 = SKILL.md 索引条目数
- [ ] MAINTENANCE.md 类型映射表行数 ≥ pitfalls 文件数
- [ ] 版本号三处一致（SKILL frontmatter / MAINTENANCE 示例 / README 版本历史顶部）

### 7. 生成更新报告

输出结构化的更新报告：

```markdown
## 经验提取报告

### 新增踩坑记录
- [问题名称] → pitfalls/[filename].md

### 新增项目案例
- [项目名称] → examples/[filename].md

### 更新的文件
- SKILL.md（版本 X.X.X → X.X.X）
- MAINTENANCE.md（文件树/类型映射表/版本示例）
- README.md（统计/文件树/案例/踩坑索引/版本历史）
- pitfalls/[filename].md（新增 N 个问题）
- examples/[filename].md（新建）

### 同步检查清单结果
- [ ] 三处文件树一致
- [ ] 统计数字一致
- [ ] 版本号三处一致
- [ ] 索引条目数 = 实际文件数

### 建议的后续优化
- [优化建议 1]
- [优化建议 2]
```

### 7.5 脱敏审查（push 前强制 gate）

**重要**：本仓库是公开 GitHub 仓库，从真实项目提取经验时，此步骤为强制 gate，**任何一项未通过则禁止 commit/push**。逐项检查本次新增/修改的所有内容：

#### 7.5.1 识别类信息
- [ ] 部门/组织/公司名 → 替换为 `[部门]` / `[公司]` 或删除
- [ ] 真实用户群体描述（可能暴露业务方向）→ 泛化为"目标用户" / "内部用户" / "开发者"
- [ ] 团队规模/人数 → 删除，或改为量级（"小团队" / "中型团队"）
- [ ] 内部系统/服务/工具名 → 替换为 `[内部服务]` / `[内部工具]`

#### 7.5.2 技术类信息
- [ ] 内部 API 端点/域名 → 替换为 `https://api.example.com`
- [ ] 内部仓库/包名/路径 → 替换为占位符（`@internal/pkg` → `@scope/pkg`）
- [ ] 内部文档/Wiki 链接 → 删除或替换为公开链接
- [ ] 代码中的内部配置项（密钥名、内部 feature flag）→ 删除或重命名

#### 7.5.3 数据类信息
- [ ] 真实业务数据样例 → 替换为合成数据
- [ ] 真实日志/报错片段 → 脱敏（去除用户标识、内部路径）
- [ ] 数据库表名/字段名（内部约定）→ 替换为通用名

#### 7.5.4 个人信息
- [ ] 邮箱/手机号/工号/IM 账号 → 删除
- [ ] 真实姓名 → 替换为角色（"后端同事" / "PM"）
- [ ] 个人仓库/社交链接 → 删除（除非本人自愿署名）

#### 7.5.5 脱敏声明

在新增的 project-example 文件末尾填写：

```markdown
### 脱敏声明
- 审查人：[Agent / 姓名]
- 审查日期：[YYYY-MM-DD]
- 已检查项：识别类 / 技术类 / 数据类 / 个人信息
- 残留风险：[无 / 说明]
```

**通过 gate 后**：在更新报告中标注"脱敏审查：✅ 通过"，方可进入第 8 步。
**未通过**：返回修改，重新审查，不得跳过。

### 8. 提交到 Git（review gate，不自动 push）

**重要**：v2.5.0 起取消自动 push。本仓库为公开仓库，经验一旦推送即不可逆（即使删除提交也能被检索）。改为两段式 review gate：

#### 8.1 生成提交预览（自动）

输出建议的提交命令，**不执行**：

```bash
# 待执行的提交（请人工 review 后确认）
git add SKILL.md MAINTENANCE.md README.md \
        pitfalls/[filename].md examples/[filename].md
git commit -m "docs: 提取 [项目名称] 项目经验

- 新增 N 个踩坑记录
- 新增项目案例
- 三处索引同步（SKILL/MAINTENANCE/README）
- 脱敏审查：✅ 通过
- 版本 X.X.X → X.X.X"
```

#### 8.2 人工确认（必需）

向用户输出**变更摘要 + 脱敏审查结果**，明确询问：

> 本次变更涉及 N 个文件，脱敏审查已通过。是否提交并推送到 GitHub 公开仓库？
> - 确认推送 → 执行 8.1 的命令 + `git push origin main`
> - 仅提交不推送 → 只执行 commit，保留本地 review 余地
> - 取消 → 回滚所有改动

**未经用户明确确认，禁止执行 `git push`。**

#### 8.3 推送后复核（推荐）

推送后 24 小时内，人工浏览 GitHub 上的变更内容，最终复核。如发现遗漏的敏感信息，立即：
1. 删除相关内容（不是删除整个提交）
2. 强制推送覆盖（`git push --force`，需用户明确授权）
3. 假定已被爬取，评估是否需要通知相关方

## 注意事项

1. **避免重复** - 检查是否已有类似的踩坑记录
2. **保持简洁** - 每个踩坑点控制在 200-300 字
3. **代码示例** - 提供可直接复制的代码片段
4. **验证清单** - 每个问题都要有验证步骤
5. **渐进式披露** - SKILL.md 只保留索引，详细内容在子文件
6. **脱敏优先** - 从真实项目提取时，第 7.5 步为强制 gate，不得跳过；宁可过度脱敏也不可遗漏
7. **三处同步** - 新增内容必须同步更新 SKILL/MAINTENANCE/README，不得只更新主文档
8. **不自动 push** - 公开仓库不可逆，push 前必须人工确认（第 8 步）
